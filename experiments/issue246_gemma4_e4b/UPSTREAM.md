# Pinned upstream triage

Read-only research was supplied by `upstream-triage` and incorporated into execution. These are released-source leads, not measured speed claims. Primary candidate is [b11537](https://github.com/ggml-org/llama.cpp/releases/tag/b11537), commit `8e2d31e0eb658d0382d3106a61369dff81f0c080`. Conditional follow-on is [b11630](https://github.com/ggml-org/llama.cpp/releases/tag/b11630), commit `6868a52cb337450658006ad2f9281c2eb63f1666`. Both are published GitHub pre-releases, not stable-release guarantees. Baseline is b10423 / `a94d563ed801d1da1b8c2432946de07d0231bb3d`. The primary candidate includes 1,114 intervening commits according to GitHub compare; triage was targeted, not an audit of every change.

## PLE and loading

- [fac889fb / #27794](https://github.com/ggml-org/llama.cpp/commit/fac889fb38fd0e267636bd95bf096555e45b2270) introduced lazy-tensor marking and excluded lazy ranges from whole-file upfront prefetch.
- [25781383 / #27837](https://github.com/ggml-org/llama.cpp/commit/2578138397d7b422bb0e160efdd429976c55fb55) separates lazy/non-lazy buffer contexts and assigns lazy tensors to CPU default buffers. [bebc9350 / #27969](https://github.com/ggml-org/llama.cpp/commit/bebc9350ecc42a31ad119da1513998386671cf5b) renamed the control to `--lazy-mode`.
- [185103dc / #29599](https://github.com/ggml-org/llama.cpp/commit/185103dcf53222165ecd15ce8e406606e25bd091) adds lazy-only row prefetch. [Windows implementation](https://github.com/ggml-org/llama.cpp/blob/8e2d31e0eb658d0382d3106a61369dff81f0c080/src/llama-mmap.cpp#L844-L929) uses `PrefetchVirtualMemory`, after page-aligning/sorting/merging ranges. It is host file-page acquisition, not DirectStorage, guaranteed residency or a GPU-resident cache. Missing API is a no-op.
- [8e2d31e0 / #30160](https://github.com/ggml-org/llama.cpp/commit/8e2d31e0eb658d0382d3106a61369dff81f0c080) orders GET_ROWS at the graph front. [Candidate Gemma graph](https://github.com/ggml-org/llama.cpp/blob/8e2d31e0eb658d0382d3106a61369dff81f0c080/src/models/gemma4.cpp#L159-L189) performs PLE gather before ordinary embeddings. [Baseline graph](https://github.com/ggml-org/llama.cpp/blob/a94d563ed801d1da1b8c2432946de07d0231bb3d/src/models/gemma4.cpp#L421-L474) already has host-side PLE lookup/input projection; do not credit the version update with inventing PLE. Per-transformer-layer PLE gate/project operations are distinct and follow layer execution.
- [Lazy eligibility](https://github.com/ggml-org/llama.cpp/blob/8e2d31e0eb658d0382d3106a61369dff81f0c080/src/llama-model-loader.cpp#L1077-L1114): AUTO requires an individual marked tensor strictly greater than 4GiB and mmap support. ON bypasses the size threshold; no quantization whitelist is imposed. Actual Q4 GET_ROWS compatibility still needs execution. The entire fixed GGUF is 4,215,695,776 bytes, smaller than 4GiB; measured PLE table is 1,585,446,912 bytes, Q4_0. AUTO cannot activate on this artifact. Actual help and logs must corroborate.
- [b9f3599f / #30405](https://github.com/ggml-org/llama.cpp/commit/b9f3599fb1c429e89248f042699ea2e062a32e57), included only in b11630, subtracts foreign contexts from backend-owned mmap ranges. It can matter if broad host-import ranges pin unrelated lazy/CPU tensors. Source comments specifically motivate Metal; a Windows Vulkan benefit is not assumed. This follow-on is justified here by b11537 ON showing a broad CPU mapped range plus a separate lazy mapping without a measured warm memory gain.

ON versus OFF changes lazy acquisition, buffer assignment and mapping behavior together; it is not a pure row-prefetch ablation. No released purpose-built Vulkan-resident E4B PLE cache was found. No alternative PLE precision artifact was necessary for the fixed-Q4 question.

## Other relevant released changes

## Claims not carried into the experiment

[PR28136](https://github.com/ggml-org/llama.cpp/pull/28136) and [PR29030](https://github.com/ggml-org/llama.cpp/pull/29030) are closed, unmerged direct-read experiments. Their historical `on-direct` option is not supported by either selected candidate. Released row prefetch is not equivalent to those direct-read patches.

The concrete [Windows Gemma prefetch report](https://github.com/ggml-org/llama.cpp/pull/29599#issuecomment-5888102168) uses BF16 E4B, a 5.25GiB table, RTX5090/CUDA and cold cache. [Vulkan reports in that thread](https://github.com/ggml-org/llama.cpp/pull/29599#issuecomment-5888189189) use Qwen on different hardware. [Embedding graph discussion](https://github.com/ggml-org/llama.cpp/pull/30160#issuecomment-6085766207) includes CUDA/Metal regression recovery, not b10423→b11537 CPU/Vulkan proof. [Historical direct-read Gemma results](https://github.com/ggml-org/llama.cpp/pull/28136#issuecomment-5516528132) included no gain/small regression. None predicts this task's result.

Prior MTP issues [24482](https://github.com/ggml-org/llama.cpp/issues/24482), [24623](https://github.com/ggml-org/llama.cpp/issues/24623), [24596](https://github.com/ggml-org/llama.cpp/issues/24596), [24492](https://github.com/ggml-org/llama.cpp/issues/24492) include stale-bot closure, not a blanket stability guarantee. Exact artifacts/build/backend must pass local gates.
