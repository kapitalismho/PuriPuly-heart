# Issue 246 execution protocol

Execution baseline: `7a8151be6114a950f062e2430bd36f899d57e4de`, initially clean. Product sources, shipped pins/defaults, index, history and remotes are read-only. This task-local directory is the durable experiment surface. Binaries, archives, cache files and mutable app state stay outside the repository under a dedicated external root.

## Gates and measurement boundaries

1. Verify Q4 target and existing compact drafter against the repository manifest; inspect GGUF metadata/tensors. Download and hash official b10423 and b11537 CPU/Vulkan archives, all extracted file identities, actual binary help/version/device output.
2. Compatibility/quality first: complete twelve fixed synthetic multilingual translations on each update-only arm. Inspect outputs for meaning, names, numbers, negation, format, corruption and reasoning leakage. Mechanical markers flag review rather than replacing semantic assessment.
3. Same target/drafter and current profile: mmap; total context 4608; three pinned slots; batch/ubatch 512; f16 KV; reasoning off; priority -1. Persisted CPU 4/12, draft1/1, max/min3/2, p-min0, FA off, MTP on. Vulkan4/4, full offload, FA on, MTP off. Do not infer effective options from old help.
4. Tuning uses three separate development examples in `measure.py`. Final timing uses the first three evaluation examples, rotating English→Korean, Korean→English, Japanese→English across three retained slots. Additional quality/transition cases cover Chinese and more pairs/LRU pressure. Settings are frozen before final runs.
5. PLE uses the unchanged selected Q4. Test supported candidate `auto`, `on`, `off`; baseline without a lazy-mode control is not given a historical invented flag. Record real eligibility and buffers. Hashing/earlier reads warm the OS cache; no OS-cold claim is authorized. Startup/readiness and first prefix prefill are diagnostic observations, not hot latency.
6. Bound tuning by measured bottlenecks. Quality/stability failure excludes an arm. Meaningful repeated requests, multiple fresh server/app processes, slot/prefix transitions, process memory and controlled contention are required before a recommendation. If a change is below spread, dominated or upstream-blocked, stop that branch.
7. Actual-app confirmation uses current capabilities and typed CLI mutations, observes terminal translation/publication and effective backend, then fresh-process restart/cache behavior and shutdown. No GUI claim. Existing live PuriPuly is untouched. Candidate runtime identity may be injected process-locally for safe intended prefix-key testing; unmodified experimental root override retains shipped identity and is not safe cross-version cache integration.

## Frozen workload

`measure.py` defines twelve evaluation inputs and three disjoint tuning inputs before inference. All are synthetic. Current non-sensitive product prompt assembly and user-message serialization are imported from this checkout, with fixed five-line synthetic history and `People: 2`. Per-language rendered prompt files and hashes are retained. No output-length truncation benchmark is used: normal EOS/stop completion is required; 128 tokens is a safety ceiling, and reaching it fails the quality gate.

Performance sampling is temperature0.6 (current app), seed42, with actual effective remaining generation settings retained from the producer. A separate temperature0 deterministic sanity arm may compare candidate kernels/MTP. Standalone SSE observes TTFT; actual app uses non-streaming HTTP and is reported separately. Wall begins before `/apply-template` and ends after terminal `/completion` SSE. Prefix preparation and server readiness are measured independently, so hot wall does not include pair-admission preparation. Transition preparation costs must be read from each run's prefix records, not silently treated as zero.

Each request retains actual output, terminal flags, token/timing telemetry, wall, TTFT, template overhead, CPU time and process memory. Sampled request peaks use 25ms observations; OS lifetime peak counters are separate. CPU utilization uses one-core=100%, not whole-machine=100%. GPU dedicated/shared counters are queried at phase boundaries; missing counters are explicit. Mapped bytes identify OS region observations and do not imply physical residency. Producer text is retained as `.txt` because repository policy ignores `.log`.

## Environment policy and known limits

Actual host: Windows11 Education22631, Ryzen7 9800X3D8C/16T, two16GiB DDR5-5600 DIMMs, RX7900XTX24GiB, AMD26.8.1 Vulkan driver. Existing High Performance power plan is left unchanged. Unrelated desktop processes remain untouched; host utilization is sampled before/after each arm. Only owned inference and synthetic load processes are started/stopped. Serial inference avoids sibling measurement contention. No private application settings or conversation contents are read; only the explicitly permitted numeric thread-profile file is read.

No change in this experiment is a production rollout authorization. A positive candidate recommendation remains conditional on separately integrating the pin/build identity and preserving cache invalidation, followed by production acceptance.

## Bounded adaptive decisions

- AUTO/OFF full repeated timing was pruned after actual table eligibility, help and producer buffers agreed. OFF received three completion sanity requests per backend. ON received the same eighteen-request development workload as AUTO; it activated lazy reads/prefetch but did not establish a warm benefit. This is explicitly not a cold-OS-cache verdict.
- Changing synthetic history exposed substantial native prompt/checkpoint-cache retention. `--cache-ram 0` became a separate resource-policy tuning arm, never part of update-only. Three native slots, per-slot context checkpoints, and application disk-cache policy remain unchanged. CPU FA-on was compared only within that cache0 development arm and was slower; finalists retain CPU FA-off. Final cache0 comparison uses the already-frozen evaluation inputs and separate fresh-process repetitions.
- The b11630 follow-on tests only the supported ON placement path, prompted by the broad mapped ranges in b11537. It is not a second full version search. No alternative tensor precision, whole-model quantization, vendor backend or Vulkan MTP arm was opened.
- Default-cache soak requests are bounded to96 per backend/revision; cache0 finalist soaks request200. Soaks stop explicitly if available physical RAM falls below1536MiB or owned process private commit exceeds14GiB. Such a stop remains in run metadata and is not called a crash or a proven leak. Repeated memory bins and native eviction/cache-size records distinguish bounded retention from unbounded growth where the observation window permits.
- One initial actual-app arm had terminal-degraded language settings because an unrelated idle Soniox constructor required a credential. That failure is retained. Authorized corrected app probes place only a synthetic nonworking construction token in the isolated encrypted store, never verify it or enable capture, and fail-close non-loopback Python DNS/connect/connect_ex attempts. This is a controlled unused STT/network boundary, not a translation substitution; no Soniox readiness claim is made.
- Actual-app restore HTTP success, native bytes/checkpoints restored, effective cached prompt tokens, and completed translation latency are separate observations. Matching first synthetic input is repeated after a genuinely fresh host/native process. Fresh-prefix preparation plus first translation is kept separate from OS-cold loading. Baseline and candidate restoration cannot be declared equivalent from HTTP status alone.
- Primary controlled history is not byte-identical resolver output: it omits bullets/quotes. Preserve the original measurements, and use a separate paired literal confirmation through the real five-entry/60s resolver/filter rather than silently changing the workload. Actual-app warm turns exercise the unmodified real resolver.
- Automatic sanity/token parity is not semantic correctness. Independent review found shared after-lunch→after-noon ambiguity in the original12-case gate, plus shared ticket-count attachment/hearsay concerns in literal rows. These qualify any recommendation; no prompt/model repair or extra quality sweep is in scope. Historical quality rows lack a captured full context/user hash; retain definition provenance without inventing one.
- Standalone exit_code1 is deliberate Windows terminate with owned process exit observed, not graceful shutdown or evidence of a crash by itself. Initial CPU contention observed launcher-only counters; separately named corrected controls pin/account the whole owned process trees. Failed/limited observations remain in the ledger.
