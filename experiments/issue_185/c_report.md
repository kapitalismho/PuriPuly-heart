The dispatcher fences current worker generation, channel, discard reason, and outstanding future before settling the valid response. It settles before scheduling WAV unlink. The sole runtime owns at most one outstanding cleanup task; the next dequeue waits for it, so a stuck deletion imposes bounded backpressure rather than accumulating WAVs. Shutdown, worker failure, channel-cancel escalation, and decode recovery drain it before temporary-directory cleanup. The worker has finished using that path before unlink starts. The scoped adapter's native request task remains owned until its response; closing a channel still invalidates publication. A failed unlink emits a failure diagnostic and does not replace the already valid transcript. If the channel remains active, the runtime faults before dispatching a successor (queued jobs retire as failures) and drains the worker and residual directory; this prevents repeated failed deletions from accumulating unbounded files. ## Consolidated repair on `78d588a5998ca3486c0ea2e8e469aa3b90e43de5`

The review found that the dispatcher retained the runtime-owned PCM payload after publishing a logical result and that cancelling a shutdown waiter interrupted teardown while WAV deletion was held. The new WAV stage releases both its local payload reference and the active work's payload immediately after owned-thread staging completes, before the worker response can settle. The worker uses the already-staged WAV; no file/native lease is released early. A direct-runtime gate test takes a weak reference to the runtime's copied 320,000-sample float32 allocation during WAV staging, then holds unlink after the result and proves that allocation has been released while the WAV cleanup remains pending. This is allocation-ownership proof rather than an end-to-end latency measurement.

Last-channel deactivation and application close now share one runtime-tracked shutdown task, shielded from cancellation of any individual caller; the task owns worker stop, temporary-file drain, lifecycle-task gathering, and final scope close. The close intent is retained even if its waiter is cancelled, and rejoined callers await the same task. A cancelled last-channel waiter cannot enable a replacement worker until old cleanup and native shutdown finish. Successful result publication still precedes unlink, while bounded one-file cleanup and one-worker inference remain unchanged.
