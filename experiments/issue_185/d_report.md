**Clock validity is the main finding.** WASAPI #21's PA `currentTime` pairs tightly with callback `time.monotonic` (host − current median ~0.018–0.019 ms, 3-second first/last offset drift ~−0.02 to −0.05 ms), but `inputBufferAdcTime` is **10 ms *later* than currentTime** in essentially all callbacks (one 20-ms exception); all 1,197 callback pairs fail ordering. WDM-KS #33 has currentTime and host readings close (median host − current ~.04 ms) but its ADC starts at **0 seconds** and advances relative to stream start while currentTime starts near process-monotonic ~39,000 seconds: 1 nonpositive and 29/242 otherwise incompatible-domain callbacks per high/low run. Its apparent 39,000-second age is rejected, **not** an input-delay measurement. The probe rejects reversed PA ordering and >1-second apparent clock-domain differences; no valid end-frontier `currentTime − (ADC + frames/rate)` estimate is available. Even when currentTime approximately aligns with host monotonic, that does not calibrate ADC. Physical input snapshots occasionally have one callback with no admitted frame, so index-only callback-to-source timing cannot be used to reconstruct per-frame ADC age there. Do **not** substitute these values into canonical timestamps or the 400-ms grace.

The mapped source-to-VAD-ready proxy is callback-host span timing *after* acoustic acquisition; it exercises production `SoundDeviceAudioSource` → `CaptureMappedStreamingResampler` → 512-sample block availability but does not run Silero and cannot see pre-callback sample age. F separately observes real VAD invocation for synthetic frames. `stream.latency` is a driver estimate, not measured acoustic age. WASAPI did not honor low as a changed stream estimate/block cadence on this virtual input; WDM-KS changed its estimate and cadence strongly, yet neither validates pre-callback latency due to invalid ADC clocks. One idle 2–3-second pair is not a guarantee of stability or underrun behavior under load. No raw private audio stored; callback frames remained transient in process.

**Disposition/decision required:** maintain current open request and canonical clock pending a representative VRChat-load run and a trustworthy device-specific sample-age reference (e.g., validated loopback calibration or verified PA host-driver clock interpretation). Maintainer must decide any low default/fallback or timestamp migration; this investigation does not authorize it. The WDM-KS result makes low a scoped *candidate*, not a universal recommendation. Other installed devices/host APIs, headset runtime, and HMD display remain untested.
