## Decision and ownership

Previous scoped GPU path: source float32 -> shared `float32_to_pcm16le_bytes` -> adapter PCM16-to-float32 allocation -> adapter `.copy()` for retention -> float32 concatenation on seal -> runtime contiguous float32 `.copy()` -> float32-to-PCM16 WAV staging. The new scoped GPU path retains immutable PCM16 `bytes` chunks, joins them once at seal, transfers the immutable result to the existing bounded shared runtime, and converts to float32 only at WAV staging for the **existing second quantization**. This removes the per-payload float32 allocation/copy, the float32 concatenation, and the additional runtime float32 copy. A `bytearray` sender is copied at admission; frozen `bytes` may be reused without a duplicate retained allocation. `send_audio_f32` legacy/direct calls still copy producer-owned mutable arrays; runtime's direct float32 `submit()` also copies for asynchronous producer reuse. The existing scoped retention profile remains conservatively charged at four bytes/sample until terminal, despite the two-byte retained PCM16 representation; PCM age/TTL, identity, sequence and context-only designation remain with the scoped engine. All source/channel/model admission remains in the existing owners.

Direct writing of the *first* PCM16 quantization to WAV was **not** adopted. Existing WAV samples derive from `round(clip(pcm16 / 32768, -1, 1) * 32767)`, which can differ from the original PCM16 integer (e.g. both saturation endpoints). The final WAV path retains this exact formula. The actual-owner before/after probe asserts byte-identical WAV payload; `h_probe.py` also enumerates **all 65,536 PCM16 codes** and checks equality against the original two-quantization path. Remote PCM16 wire conversion in `ScopedRecognitionEngine` is untouched. The common engine's first quantization is the preserved input contract, not a removable copy without an input-value decision.

Local Qwen still needs the shared PCM16-to-float32 conversion because sherpa receives float32 values quantized by `pcm / 32768`; changing it to original unquantized float32 would silently alter recognition input. For the standard PCM16 `send_audio` path, that conversion already produces a newly owned array, so a second `.copy()` was redundant and removed. Direct `send_audio_f32` still copies untrusted producer buffers. The scoped session/budget and decode coordinator remain unchanged. A queued producer-reuse regression mutates both PCM16 bytearray and direct mutable float32 input and checks decoded values after the producer has overwritten them.

## Measured bounds and verification

Fixed 16,002-sample representation comparison in `c_after.json`: original-chain median **72.05 μs** and `tracemalloc` median peak **288,889 bytes** versus equivalent bytes-retention chain median **68.55 μs** and peak **256,822 bytes** (40 paired iterations, Python 3.14.7, NumPy 2.5.1, Windows 11). `c_before.json` captured the actual old-owner WAV before the change; its separate original-chain median was **69.1 μs**, peak **288,825 bytes**. Qwen's isolated PCM16-to-float32 conversion plus redundant `.copy()` versus conversion alone, 100 iterations: **22.15 vs 20.8 μs median**; both showed the same **128,420-byte median peak**, since conversion intermediates dominate the peak (the removed retained array copy is 64,008 bytes for this input). These are tiny workload-specific isolated costs, **not** measured dispatch/display gain or a quality improvement. Tests `test_gpu_asr.py`, `test_local_gpu_backend.py`, `test_local_qwen_sherpa.py`, and `test_stt_scoped_engine.py` passed in the final focused run; in particular real owner+adapter test checks original quantized WAV bytes for saturation and half-range codes, asynchronous producer mutation, and bounded terminal/cleanup behavior. No GPU model was installed, so worker/IPC performance and any broader hardware effect remain unknown.
