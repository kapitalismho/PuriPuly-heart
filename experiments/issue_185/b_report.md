# Issue 185 — Outcome B: racing LLM result versus cleanup

## Status and scope

Implemented locally in `src/puripuly_heart/core/llm/fallback_racing.py` and the narrowly required `core/llm/provider.py` semaphore owner. Baseline execution revision: `78d90ca9722d3c88e05448bbe7c958892c5b11ec` (ancestor `origin/dev` at `b6dab6fc`); candidate is the modified worktree based on that revision, not a committed integration revision. This record covers B only, not A/C-H or integrated acceptance.

The existing racing owner now hands a winner to its caller before grace and loser cancellation complete. The same owner retains the scheduler, provider branches, operation and cleanup tasks, consumes late exceptions, and drains cleanup before closing each underlying provider once. A selected winner fences scheduled attempts; grace remains the configured duration when the race is not closing. Closing stops ingress, cancels admitted provider work and drains it before provider closure. A cancelled close waiter leaves the owner-owned shutdown running; a cancelled translation caller hands work to the same cleanup owner. The existing provider-wide semaphore permit transfers to that cleanup for races and releases only on actual completion; non-racing providers keep their existing `async with` path. There is no extra request/session and no new reaper or concurrency ceiling.

## Reproduction and checks

- Before implementation, the corrected gate-controlled regression `test_winner_reaches_consumer_before_loser_cleanup_and_close_drains` printed `F` with the selected winner blocked by a held loser cancellation; that invocation timed out after 20 seconds during teardown because the gate was not yet released on test failure. This is a deterministic barrier proof of the wait, **not** a 20-second production latency measurement. An earlier draft had a cancellation-susceptible gate; the retained test now releases its gate in `finally`.
- After implementation, `tests/core/test_fallback_racing_llm_provider.py`, `tests/core/test_hedged_attempts.py`, and `tests/core/test_llm_semaphore.py` passed together. The changed old assertions now wait for actual loser completion rather than assuming cleanup preceded the returned winner. Cases include held cancellation, close and cancelled close, waiting/cancelled admission, caller cancellation, grace, hedging, terminal errors, duplicate close, and normal-provider semaphore behavior.
- `experiments/issue_185/b_probe.py` exercises the actual `SemaphoreLLMProvider(FallbackRacingLLMProvider(...))` owners with synthetic providers and an opt-in private winner-selection timestamp callback (no speech/credentials logged). Run: repository Python 3.14.7, `PYTHONPATH=src`, no network/API calls; the script writes `b_after.json`. The one deterministic barrier sample used semaphore capacity 1, loser grace 10 ms (probe override; not a production setting), immediate winner hedge, a scheduled third attempt at 25 ms, and a deliberately held loser cancellation. The third attempt did not start even after crossing its deadline. Provider calls `[1,1,0]`, closes `[1,1,1]`; permit stayed occupied through cleanup and was acquirable afterward.

## Intervals and interpretation

The latest recorded one-sample Windows host `time.monotonic_ns()` observations in `b_after.json` were **provider-response-ready → winner-selection 0.016 ms**, **selected winner → consumer-return 0.017 ms**, and **selected winner → loser cleanup completion 41.951 ms**. These intervals are deliberately separate; the last includes the probe's artificial 40 ms hold and scheduler time, so it is not provider or field latency. The baseline gate did not yield a finite winner-return observation before loser release; it proves dependency rather than a numeric before/after saving. No ASR, prepared-context, ordered output, physical overlay/HMD, or complete pipeline gain is claimed. Production policy's fixed 50 ms loser grace and retry/hedge configuration were not changed; probe settings are diagnostic only.

## Residual gaps

This is deterministic ownership/handoff evidence, not a paid-provider, Windows VRChat, clock-synchronized physical display or multi-sample latency benchmark. Integration revision and combined A-H acceptance remain outside this local B report. Cancellation-resistant providers that never finish after being cancelled necessarily keep their permit and block orderly close: cancellation does not prove external native work stopped. No timeout or forced lease release was introduced. The existing provider-wide semaphore is the finite admission/debt bound in the composed runtime; direct use of the racing provider without that configured wrapper retains its pre-existing unrestricted caller admission. No shared public contract or policy decision was required.
